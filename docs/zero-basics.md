# 零基础：这套技术架构怎么搭起来的

> 写给第一次读这份代码的人。不需要懂 Tender 的模型，但读完应该能在脑子里把整条链路跑一遍。

## 先说清楚有几个「东西」

这套系统不是一个程序，是四个东西各干一件事：

| 谁 | 语言 | 在哪 | 干什么 |
|---|---|---|---|
| 鱼鱼（蓝色大肥鱼） | C# | 你的桌面 | 显示形象、说话、做动作 |
| 心跳插件 | JavaScript | DSH 里面 | 每轮对话结束，把这一轮交给 Tender |
| Tender | Python | 本机 8080 端口 | 算「现在是什么状态」 |
| 记忆边车 | Rust | 本机 8090 端口 | 长期记住「发生过什么」 |

它们之间只靠两样东西联系：HTTP 请求（一段固定的 JSON）和一个 JSON 文件。

为什么不用一个程序全干了？因为它们的更新节奏完全不同。鱼的动画一秒几十帧，状态一秒一次，记忆几小时才动一次，而算法模型可能几个月才换一版。硬塞进一个进程，改任何一处都要重启全部。

## 一条请求是怎么走的

你在对话框里打了一句「今天特别焦虑，题又做不完」，按回车。接下来发生的事，按顺序：

```
1. DSH 收到这句，放进这个会话的收件箱
2. 插件听到「收件箱有消息」，把正文记在内存里
3. 这一轮结束时，插件触发「轮次即将关闭」事件
4. 插件取正文 → 截前 60 个字 → 算 SHA-256 指纹
5. POST http://127.0.0.1:8080/heart/beat   带上摘要和指纹
6. Tender 把这条写进 SQLite 的 events 表
7. Tender 取出最近 24 小时、最多 12 条事件
8. Tender 从文本里认情绪词，算出情绪倾向与置信度
9. Tender 组装「状态卡」，同时把摘要写进记忆边车（失败也不报错）
10. Tender 把状态卡返回给插件
11. 插件把状态卡里的情绪标签翻成 mood（焦虑 → 烦躁）
12. 插件调大肥鱼自己的情绪模块，写入 mood 与强度
13. 插件把 mood 写进鱼鱼的人设文件里的标记块
14. 下一轮鱼鱼开口前读人设，于是语气变了
```

第 5 步和第 12 步是两个关键的分界线：左边是我们自己的代码，右边是别人的系统。跨过去的时候，只传约定好的字段。

## 第 5 步：那个 HTTP 请求长什么样

请求体大概是这样（`…` 表示省略）：

```json
{
  "learner_id": "dafeiyu",
  "event": {
    "kind": "conversation",
    "summary": "今天特别焦虑，题又做不完",
    "evidence_hash": "sha256:9f3c…",
    "attrs": { "source": "dafeiyu-heart-plugin", "channel": "dsh" }
  },
  "consent_scopes": ["companion_support"]
}
```

四个字段各有原因：

- `summary` 截断在 60 字，因为要在「够判断情绪」和「不搬原文」之间取平衡；
- `evidence_hash` 是这句话的指纹，用来事后核对「这条状态是依据哪句话算的」，但它反推不出原文；
- `attrs` 放来源渠道，方便以后区分「主对话」和「B 站私信」；
- `consent_scopes` 记录这次用了什么授权范围。

返回的是一个「状态卡」，里面有 `summary`（一句话结论）、`confidence`（置信度 0–1）、`hypotheses`（几条假设和证据）、`emotion_context`（情绪标签与强度）。

## 第 7 步：为什么是「24 小时 + 12 条」

这是全系统唯一一个真正需要判断的取舍。

看全部历史，一次崩溃会把她之后一整天的语气都压住。只看最后一条，一句随口的话就能翻掉她的状态。所以两头都限：

- 时间窗 24 小时：昨天的事自然滑出去；
- 条数窗 12 条：密集聊天时也不会被淹没。

两者都空的时候（比如两天没说话），退回最近 12 条，避免她变成一张白纸。

两个数字都能用环境变量改：`HEART_WINDOW`、`HEART_WINDOW_HOURS`。

## 第 9 步：记忆为什么会落在另一个进程

一开始想法很简单：Tender 自己存不就完了。但翻开它用的那个数据库（DaoQL-Edu）会发现两件事：动态属性 `attrs` 不落盘，向量索引从来没有被写入过。

也就是说，那个库能记住「谁、和谁、什么关系、什么时候」，记不住「这件事具体是什么」，也做不了语义检索。

于是拆开：**图与关系交给 DaoQL-Edu，内容与向量交给边车**。边车用 redb 存 JSON 和向量，召回时做余弦相似度排序。两边用同一个实体 id 对齐。

这样做的好处是上游一行没改，坏处是多一个进程。权衡之下选前者，因为那是别人维护的教育项目，改了以后每次同步上游都要重新打补丁。

## 第 12–13 步：为什么不直接改她的心情文件

她的情绪存在一个 JSON 文件里，理论上直接写就行。但那个文件有自己的规则：半衰期 18 小时的衰减、取值范围的裁剪、历史记录的白名单校验。

绕过它直接写，短期看着能用，长期会跟她的动画、状态页、备份机制对不上。所以插件调的是她**自己的写入函数**，交给她自己去衰减和校验。

同理，心情传给她的话不是改情绪文件，而是改人设文件里的一小段带标记的文字：

```
<!-- tender-mood:start -->
【当前心情】温暖（warm），强度 54。语气跟着这个心情走。
<!-- tender-mood:end -->
```

标记的作用是「可替换」：每次心跳只替换标记之间的内容，她原来的性格描述一个字不动。

## 数据落在哪

四份数据，四个地方：

| 数据 | 位置 | 生命周期 |
|---|---|---|
| 事件（摘要 + 指纹） | Tender 的 SQLite `events` 表 | 永久 |
| 实体与关系 | 边车的 DaoQL-Edu 图库 | 永久 |
| 内容与向量 | 边车 `memory.redb` | 永久 |
| 心情与历史 | `emotional-state.json` | 18 小时衰变 |
| 当前心情文字 | 鱼鱼人设里的标记块 | 每次心跳覆盖 |

前三个是「证据」，后两个是「表现」。证据不动，表现随时变。

## 一台机器上跑起来要几步

1. **起两个服务**：Tender 监听 8080，边车监听 8090。脚本 `scripts/start-services.ps1`。
2. **装插件**：它注册在两个事件上——消息进入收件箱、轮次即将关闭。装完自动工作。
3. **开小窗**：左下角一块文字卡，每 2 秒读一次心情文件，只在值变了才重绘。

三个都能单独停，停了只影响自己那一环。

## 坏了会怎样

设计时就假定每一环都会坏：

- **Tender 不通**：这一轮不打点，日志记一行，对话完全不受影响；
- **边车不通**：心跳照样成功，返回里标 `memory.degraded = true`；
- **心情模块路径不对**：跳过写心情，记 `skip`，不做别的动作；
- **情绪证据不足**（置信度低于 0.2）：不更新心情，保持原样。

任何一环都不允许「假装成功」。宁可状态旧一点，也不要编一个数字。

## 想改的话，从哪下手

- **换个模型**：只动 Tender 里算状态卡那一段，插件不用改；
- **换一种记忆**：只动边车，Tender 的返回格式不变；
- **加一个渠道**（比如 B 站私信）：在 `attrs.channel` 上加值，其余不动；
- **调敏感度**：改 `HEART_WINDOW` 与 `HEART_WINDOW_HOURS`，不用碰代码。

边界画在这几处，就是为了让你改一处时不至于牵动全部。
